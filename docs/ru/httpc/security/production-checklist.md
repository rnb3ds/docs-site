# Контрольный список для продакшена

Проверка по каждому пункту перед релизом эффективно устраняет типовые дефекты конфигурации безопасности. Список сгруппирован по категориям; для каждого пункта указаны значение по умолчанию, рекомендуемое продакшен-значение и метод проверки. Рекомендуется автоматизировать проверку высокорисковых пунктов скриптом в CI (см. конец страницы).

## TLS / шифрование

| Пункт проверки | По умолчанию | Рекомендуется в продакшене | Метод проверки |
|----------------|--------------|----------------------------|----------------|
| `InsecureSkipVerify` | `false` | `false` | Поиск в коде, см. команду в конце |
| `MinTLSVersion` | TLS 1.2 | TLS 1.2+ (для высокой безопасности можно принудительно 1.3) | `grep MinTLSVersion` |
| `MaxTLSVersion` | TLS 1.3 | TLS 1.3 | `grep MaxTLSVersion` |
| Не используется `TestingConfig()` | — | Да | Поиск в коде, см. команду в конце |
| Закрепление сертификатов (высокобезопасные сценарии) | Не включено | Рекомендуется включить | `grep CertificatePinner` |

:::warning
`InsecureSkipVerify = true` делает все меры безопасности TLS недействительными. HTTPC выводит предупреждение в `stderr` вне тестовой среды — перед релизом обязательно убедитесь, что в логах нет этого предупреждения.
:::

Дополнение о семантике версий: при `MinTLSVersion`/`MaxTLSVersion` равных `0` происходит автоматический откат к 1.2/1.3; `Min > Max` не проходит проверку `New()`. После установки `TLSConfig` поля версий игнорируются, а `Security.InsecureSkipVerify` перестаёт действовать (управлять нужно внутри `TLSConfig`) — при ревью пользовательского `TLSConfig` проверяйте его собственные поля.

## Защита от SSRF

| Пункт проверки | По умолчанию | Рекомендуется в продакшене | Метод проверки |
|----------------|--------------|----------------------------|----------------|
| `AllowPrivateIPs` | `false` | `false` (при обработке недоверенных URL) | Поиск в коде, см. команду в конце |
| `SSRFExemptCIDRs` | `nil` | Точно перечислить только необходимые диапазоны | Аудит возможности сужения диапазонов |
| `SecureConfig()` для пользовательских URL | — | Да | Ревью кода |
| `RedirectWhitelist` | `nil` | Настраивать при обработке пользовательских URL | Ревью кода |

```go
cfg := httpc.DefaultConfig()
cfg.Security.AllowPrivateIPs = false
// Исключать только фактически нужные диапазоны, по возможности сужая
cfg.Security.SSRFExemptCIDRs = []string{"10.50.0.0/16"}
cfg.Security.RedirectWhitelist = []string{"api.example.com"}
```

## Настройка таймаутов

Таймауты — первая линия обороны против Slowloris, исчерпания ресурсов и каскадных сбоев.

| Пункт проверки | По умолчанию | Рекомендуется в продакшене | Метод проверки |
|----------------|--------------|----------------------------|----------------|
| `TimeoutConfig.Request` | 180s | По бизнесу (например, 30s) | Подтвердить ненулевое значение |
| `TimeoutConfig.Dial` | 10s | 5-10s | `grep Timeouts.Dial` |
| `TimeoutConfig.TLSHandshake` | 10s | 5-10s | `grep Timeouts.TLSHandshake` |
| `TimeoutConfig.ResponseHeader` | 0 | По необходимости (см. ниже) | Понять область действия |
| `TimeoutConfig.IdleConn` | 90s | 60-120s | — |

:::warning
`TimeoutConfig.ResponseHeader` — жёсткий лимит транспортного уровня, действующий на **все запросы** данного клиента; его **нельзя** переопределить по запросу через `WithTimeout`. Положительное значение перекрывает более длинный `WithTimeout`. Устанавливайте положительное значение только при необходимости независимой транспортной защиты от Slowloris; для сценариев с длинными ответами (AI API и др.) оставляйте 0 и полагайтесь на таймаут `Request`.
:::

### Как рассчитать бюджет таймаутов

`Timeouts.Request` (по умолчанию 180s) и `WithTimeout` — это **общий бюджет, покрывающий все повторные попытки и паузы backoff**: движок повторов устанавливает единый дедлайн на весь запрос, а не перезапускает таймер на каждую попытку — `WithTimeout(30s)` + 3 повтора займут максимум 30s, а не вчетверо больше. И настроенное значение, и `WithTimeout` имеют жёсткий предел 30 минут; превышение — ошибка конфигурации.

Отдельная попытка ограничена более узкими таймаутами: `Dial` (по умолчанию 10s) ограничивает установку TCP, `TLSHandshake` (по умолчанию 10s) — рукопожатие. Рекомендуется отталкиваться от P99 нижележащего API:

```go
// Формула бюджета: Request ≥ Dial + TLSHandshake + ожидаемое время передачи × (1 + MaxRetries) + сумма пауз backoff
cfg.Timeouts.Request = 30 * time.Second // Общий бюджет
cfg.Timeouts.Dial = 5 * time.Second     // Один дозвон
cfg.Timeouts.TLSHandshake = 5 * time.Second
```

## Лимиты пула соединений

| Пункт проверки | По умолчанию | Рекомендуется в продакшене | Метод проверки |
|----------------|--------------|----------------------------|----------------|
| `MaxIdleConns` (глобальные неиспользуемые соединения) | 50 | Оценить по конкурентности | Подтвердить ненулевое значение |
| `MaxConnsPerHost` (всего соединений на хост) | 10 | Повышать по мере надобности при высокой конкурентности | Помнить: 0 = без лимита |
| `MaxIdleConnsPerHost` (неиспользуемые на хост) | Выводится автоматически | — | Наследуется от `MaxConnsPerHost/2`, ограничено 2-10 |
| Общий предел пула | 1000 | — | Встроен в слой соединений; при превышении — ошибка исчерпания пула |

Жёсткие пределы валидации конфигурации: `MaxIdleConns` и `MaxConnsPerHost` — 0-1000 (`ValidateConfig`). Две легко неверно понимаемые семантики:

- `MaxConnsPerHost = 0` означает **без лимита** (семантика net/http), а не «запрет соединений»; по умолчанию задано 10
- Общий предел пула (1000) нельзя изменить через публичный `Config`; при достижении предела новый дозвон сразу падает, а не встаёт в очередь

```go
cfg := httpc.DefaultConfig()
cfg.Connection.MaxIdleConns = 50    // Глобальные неиспользуемые соединения
cfg.Connection.MaxConnsPerHost = 10 // Лимит соединений на хост (idle + active)
```

`SecureConfig()` использует более консервативные 20/5; `PerformanceConfig()` ослабляет до 100/20.

## Лимиты размеров

| Пункт проверки | По умолчанию | Рекомендуется в продакшене | Метод проверки |
|----------------|--------------|----------------------------|----------------|
| `MaxResponseBodySize` | 10MB | По бизнесу (например, 5MB) | Подтвердить ненулевое значение |
| `MaxDecompressedBodySize` | 100MB | По бизнесу (например, 50MB) | Подтвердить ненулевое значение |
| `MaxRequestBodySize` | 0 (без лимита) | **Явно установить** лимит загрузки | `grep MaxRequestBodySize` |
| `MaxResponseHeaderBytes` | 0 (умолчание Go 10MB) | В высокобезопасных можно сузить до 1MB | `grep MaxResponseHeaderBytes` |

```go
cfg := httpc.DefaultConfig()
cfg.Security.MaxResponseBodySize = 5 * 1024 * 1024     // Ответ 5MB
cfg.Security.MaxDecompressedBodySize = 50 * 1024 * 1024 // Распаковка 50MB
cfg.Security.MaxRequestBodySize = 2 * 1024 * 1024       // Загрузка 2MB (по умолчанию 0 без лимита!)
cfg.Connection.MaxResponseHeaderBytes = 1 * 1024 * 1024  // Заголовки ответа 1MB
```

:::danger
`MaxRequestBodySize` по умолчанию равен 0 (без лимита) и **не имеет автоматического резервного значения**. При проксировании или обработке пользовательских загрузок без установки злоумышленник может отправить сверхбольшой запрос и исчерпать пропускную способность и память. Обязательно устанавливайте явно.
:::

## Стратегия повторов

| Пункт проверки | По умолчанию | Рекомендуется в продакшене | Метод проверки |
|----------------|--------------|----------------------------|----------------|
| `MaxRetries` | 3 | Не более 5 | Ревью кода |
| Повторы неидемпотентных запросов | — | Осторожность с POST/PUT/PATCH | Ревью кода на идемпотентность |
| `EnableJitter` | `true` | `true` (защита от «эффекта стада») | `grep EnableJitter` |
| `MaxRetryDelay` | 30s | 30s | — |

:::warning
Повторы неидемпотентных запросов (POST создание ресурсов, PUT частичное обновление) могут привести к дублированию создания или повторным списаниям. Если бизнес не идемпотентен, устанавливайте `WithMaxRetries(0)` для таких запросов или реализуйте идемпотентный ключ на стороне сервера.
:::

### Контроль шторма повторов

Встроенный список ретраебельных кодов состояния фиксирован: 408/429/500/502/503/504 (`internal/engine/errors.go`); transient-ошибки сетевого уровня (отказ/сброс/недоступность соединения, таймаут передачи не из context) тоже повторяются. Механизмы защиты от шторма включены по умолчанию — перед релизом убедитесь, что их не ослабили:

| Механизм | По умолчанию | Действие |
|----------|--------------|----------|
| Экспоненциальный backoff | `Delay=1s`, `BackoffFactor=2.0` | Раздвигает интервалы повторов, не усугубляя положение сбойного сервиса |
| Джиттер | `EnableJitter=true` | Размывает синхронный ритм конкурентных повторов, предотвращая «эффект стада» |
| Предел одиночной задержки | `MaxRetryDelay=30s` | Backoff не растёт бесконечно |
| Уважение Retry-After | Автоматический разбор | Ожидание по указанию сервера, но **не более 60s** — чтобы вредоносный сервер не «утащил» клиента за собой гигантским Retry-After |
| Общий бюджет | `WithTimeout` покрывает все попытки | Повторы не могут выйти за общий таймаут запроса |

```go
cfg := httpc.DefaultConfig()
cfg.Retry.MaxRetries = 3                   // Жёсткий предел 10 (ValidateConfig)
cfg.Retry.MaxRetryDelay = 30 * time.Second
cfg.Retry.EnableJitter = true              // Включён по умолчанию; явная запись удобна для аудита
// Для неидемпотентных API отключайте повторы на уровне запроса:
// client.Post(url, httpc.WithJSON(body), httpc.WithMaxRetries(0))
```

:::tip
При настройке `ProxyRotateOnStatus` (ротация прокси по коду состояния при повторе) `MaxRetries` автоматически поднимается до `len(ProxyPool)-1` (не более 10), чтобы каждый прокси был попробован хотя бы раз.
:::

Ещё две распространённые ловушки: тело запроса `io.Reader` для поддержки повторного воспроизведения целиком буферизуется, и при превышении 100MB возвращается ошибка (`retry not supported for streaming bodies`); `context.Canceled`/`context.DeadlineExceeded` никогда не повторяются — явная отмена не порождает повторных запросов.

## Управление ресурсами

| Пункт проверки | По умолчанию | Рекомендуется в продакшене | Метод проверки |
|----------------|--------------|----------------------------|----------------|
| Явный `client.Close()` | — | `defer client.Close()` | Ревью кода |
| Закрытие клиента по умолчанию | — | `CloseDefaultClient()` при выходе долгоживущего сервиса | Ревью кода |
| `WithContext` для отмены | — | Да | Ревью кода |
| Освобождение тела ответа | Автоматически | Обычным запросам ручное закрытие не нужно (и невозможно) | Подтвердить, что вы не удерживаете поток сами |
| Очистка остатков Download | Автоматически | Обрыв/провал проверки автоматически удаляют неполный файл | Подтвердить, что запись на диск не выполняется в обход `Download` |

```go
package main

import (
	"context"
	"fmt"
	"log"
	"time"

	"github.com/cybergodev/httpc"
)

func main() {
	cfg := httpc.DefaultConfig()
	client, err := httpc.New(cfg)
	if err != nil {
		log.Fatal(err)
	}
	// Гарантируем освобождение пула соединений
	defer func() {
		if cerr := client.Close(); cerr != nil {
			log.Printf("Не удалось закрыть клиент: %v", cerr)
		}
	}()

	// Управление таймаутом и отменой одного запроса через context
	ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()

	result, err := client.Get("https://api.example.com", httpc.WithContext(ctx))
	if err != nil {
		log.Fatal(err)
	}
	fmt.Printf("Код состояния: %d\n", result.StatusCode())
}
```

:::tip
При использовании пакетных функций (`httpc.Get` и др.) клиент по умолчанию не закрывает соединения автоматически при выходе программы. Долгоживущие сервисы должны вызывать `httpc.CloseDefaultClient()` при изящной остановке для освобождения пула соединений. Для продакшен-сервисов рекомендуется создавать клиент через явный `httpc.New(cfg)`, самостоятельно управляя конфигурацией и жизненным циклом.
:::

### Тело ответа и временные файлы

- **Обычные запросы**: `Result` хранит уже прочитанные и скопированные байты — HTTPC внутри выполняет чтение, дочитывание-высвобождение (до `min(10MB, MaxResponseBodySize)` для переиспользования соединения) и закрытие; Body, который нужно (или можно) закрывать вручную, отсутствует
- **Большие файлы**: используйте `Download`, а не обычный запрос — потоковая запись на диск, колбэки прогресса и докачка; неполные файлы при обрыве передачи, провале проверки или ошибке записи на диск удаляются автоматически, половинных файлов не остаётся
- **`client.Close()`**: закрывает неиспользуемые соединения, распознаватель DoH и пул соединений; идемпотентен и допускает повторный вызов; запросы к закрытому клиенту возвращают `ErrClientClosed`

## Мониторинг и аудит

### Промежуточное ПО аудита (высокобезопасные сценарии)

`AuditMiddleware` генерирует структурированные события аудита и подходит для сценариев со строгими требованиями соответствия. URL в событии уже обезличен (учётные данные удалены), конфиденциальные заголовки по умолчанию маскируются.

```go
auditCfg := httpc.DefaultAuditConfig()
auditCfg.OnAudit = func(event httpc.AuditEvent) {
    // event.SourceIP / event.UserID внедряются из context
    data, _ := json.Marshal(event)
    log.Println(string(data))
}
auditCfg.Format = "json"
auditCfg.IncludeHeaders = true
auditCfg.MaskHeaders = []string{"Authorization", "Cookie", "Set-Cookie", "X-API-Key"}
auditMiddleware := httpc.AuditMiddleware(auditCfg)
```

`SourceIP` и `UserID` внедряются через ключи context `httpc.SourceIPKey`, `httpc.UserIDKey`, что удобно для связывания запроса с вызывающей стороной. `AuditEvent` содержит временную метку, метод, URL, код состояния, длительность, число повторов, ошибку, цепочку перенаправлений, заголовки запроса/ответа и другие поля.

### Промежуточное ПО логирования и метрик

|----------------|----------------------------|----------------|
| `RecoveryMiddleware()` | Включить (защита от падения при panic) | `grep RecoveryMiddleware` |
| `LoggingMiddleware()` | Включить (логи запросов) | `grep LoggingMiddleware` |

| `RequestIDMiddleware()` | Включить (трассировка запросов) | `grep RequestIDMiddleware` |

### Маскирование конфиденциальной информации в логах

HTTPC по умолчанию обезличивает все каналы вывода — перед релизом убедитесь, что обезличивание не обходится:

| Канал вывода | Поведение |
|--------------|-----------|
| Сообщения об ошибках | Учётные данные URL → `***:***`; более 20 чувствительных параметров (`token`/`password`/`api_key` и др.) → `[REDACTED]`; fragment удаляется |
| `LoggingMiddleware` | URL в логах запросов — как выше (`SanitizeURL`, отключить нельзя) |
| `AuditMiddleware` | URL событий аудита обезличен; заголовки из `MaskHeaders` маскируются |
| `Config.String()` | Маскирование учётных данных прокси-URL; заголовки не печатаются |

Контрольные точки: кастомное промежуточное ПО, печатающее исходный URL запроса напрямую, обходит встроенное маскирование — печатайте обезличенный URL или переиспользуйте `LoggingMiddleware`; `MaskHeaders` должен покрывать чувствительные заголовки вашего бизнеса (например, `X-API-Key`, `X-Auth-Token`).

## Закрепление сертификатов

В высокобезопасных сценариях (финансы, медицина) рекомендуется включить закрепление сертификатов для защиты от атак «человек посередине» при компрометации CA:

```go
pinner, err := httpc.NewSPKIHashPinner(
    "YLh1dUR9y6Kja30RrAn7JKnbQG/uEtLMkBgFF2fuihg=", // Текущий ключ
    "C5+lpZ7tcVwmwQIMcRtPbsQtWLABXhQdejna0wHFr8M=", // Резервный (ротация)
)
if err != nil {
    log.Fatal(err)
}
cfg := httpc.DefaultConfig()
cfg.Security.CertificatePinner = pinner
```

Детали настройки и сопровождения закрепления — в [TLS и закрепление сертификатов](./tls-certpin).

## Примеры кода

### Создание продакшен-клиента

```go
package main

import (
	"log"
	"time"

	"github.com/cybergodev/httpc"
)

func main() {
	cfg := httpc.DefaultConfig()

	// Таймауты
	cfg.Timeouts.Request = 30 * time.Second
	cfg.Timeouts.Dial = 10 * time.Second
	cfg.Timeouts.TLSHandshake = 10 * time.Second
	cfg.Timeouts.ResponseHeader = 0 // Полагаемся на таймаут Request, транспортный жёсткий лимит не задаём
	cfg.Timeouts.IdleConn = 90 * time.Second

	// Пул соединений
	cfg.Connection.MaxIdleConns = 50
	cfg.Connection.MaxConnsPerHost = 10

	// Безопасность
	cfg.Security.AllowPrivateIPs = false
	cfg.Security.MaxResponseBodySize = 5 * 1024 * 1024      // 5MB
	cfg.Security.MaxDecompressedBodySize = 50 * 1024 * 1024 // 50MB
	cfg.Security.MaxRequestBodySize = 2 * 1024 * 1024       // Загрузка 2MB

	// Повторы
	cfg.Retry.MaxRetries = 3
	cfg.Retry.Delay = 1 * time.Second
	cfg.Retry.EnableJitter = true

	// Значения по умолчанию для запросов
	cfg.Defaults.UserAgent = "my-service/1.0"
	cfg.Defaults.FollowRedirects = true
	cfg.Defaults.MaxRedirects = 5

	// Промежуточное ПО
	cfg.Middleware.Middlewares = []httpc.MiddlewareFunc{
		httpc.RecoveryMiddleware(),
		httpc.LoggingMiddleware(&httpc.LoggingConfig{LogFunc: log.Printf}),
		httpc.RequestIDMiddleware(httpc.DefaultRequestIDConfig()),
	}

	client, err := httpc.New(cfg)
	if err != nil {
		log.Fatal(err)
	}
	defer func() { _ = client.Close() }()
	log.Println("Продакшен-клиент готов")
}
```

func createSecureClient() (httpc.Client, error) {

## Команды проверки

Запустите следующие команды в CI или перед коммитом для сканирования высокорисковых конфигураций:

```bash
# Проверка злоупотребления TestingConfig (исключая тестовые файлы)
grep -r "TestingConfig" --include="*.go" | grep -v "_test.go"

# Проверка InsecureSkipVerify = true
grep -rn "InsecureSkipVerify.*true\|InsecureSkipVerify:\s*true" --include="*.go" | grep -v "_test.go"

# Проверка AllowPrivateIPs = true (опасно для продакшена)
grep -rn "AllowPrivateIPs.*true\|AllowPrivateIPs:\s*true" --include="*.go" | grep -v "_test.go"

# Проверка, установлен ли MaxRequestBodySize (по умолчанию 0 без лимита)
grep -rn "MaxRequestBodySize" --include="*.go" | grep -v "_test.go"
```

:::tip
Рекомендуется оформить эти команды как шаг CI: срабатывание высокорисковой конфигурации (`TestingConfig`, `InsecureSkipVerify: true`, `AllowPrivateIPs: true` в не-тестовом коде) должно блокировать сборку.
:::
