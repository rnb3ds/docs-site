# Защита от SSRF

SSRF (Server-Side Request Forgery, подделка серверных запросов) — атака, при которой злоумышленник побуждает сервер отправлять запросы во внутреннюю сеть. Последствия: кража учётных данных метаданных облачного инстанса (токены IAM-ролей), сканирование портов и сервисов внутренней сети, доступ к внутренним административным интерфейсам без аутентификации, обход межсетевого экрана для доступа к защищённым ресурсам. HTTPC включает защиту от SSRF по умолчанию, блокируя соединения с приватными/зарезервированными диапазонами IP.

## Поведение по умолчанию

```go
cfg := httpc.DefaultConfig()
// AllowPrivateIPs = false (по умолчанию) → блокируются все приватные/зарезервированные IP
```

`AllowPrivateIPs` по умолчанию `false` — SSRF-валидация на уровне диалера полностью включена. Это отличается от проверки только имени хоста в URL: HTTPC проверяет разрешённый IP при фактическом установлении TCP-соединения, что защищает от перепривязки DNS (см. ниже).

## Где выполняется проверка: три линии обороны

SSRF-проверки распределены по трём уровням: если один обходят, следующий сдерживает атаку:

| Линия | Когда выполняется | Поведение | Реализация |
|-------|-------------------|-----------|------------|
| 1. Слой предпроверки | До отправки запроса | После разбора URL — быстрая проверка по **имени хоста**: `localhost` и его варианты, IP-литералы, традиционные десятичные/шестнадцатеричные/восьмеричные записи (без разрешения DNS, нулевые сетевые накладные расходы) | `internal/security/validator.go` → `internal/validation/netutil.go` |
| 2. Слой перенаправлений | Каждый прыжок 30x | Повторная проверка имени хоста цели перенаправления (сначала белый список доменов, затем SSRF-проверка) | `internal/engine/transport.go` |
| 3. Слой соединений (диалер) | Перед установкой TCP-соединения | **Разрешение DNS → проверка каждого IP → фильтрация приватных адресов → прямое подключение к проверенному IP**, защита от перепривязки DNS | `internal/connection/pool.go` |

Типичные отказы слоя предпроверки по форме имени хоста (соединение даже не будет устанавливаться):

| Целевой хост | Причина отказа |
|--------------|----------------|
| `localhost`, `LOCALHOST`, `localhost.localdomain` | Проверка localhost-имён (без учёта регистра) |
| `127.0.0.1`, `::1`, `0.0.0.0`, `::` | Проверка localhost-имён (точное совпадение) |
| `10.0.0.1`, `192.168.1.1`, `169.254.169.254` | Блокировка приватных/зарезервированных IP |
| `2130706433`, `0x7f000001`, `0177.0.0.1` | Блокировка традиционных записей IP-литералов |

```go
package main

import (
	"fmt"
	"log"

	"github.com/cybergodev/httpc"
)

func main() {
	client, err := httpc.NewDefault()
	if err != nil {
		log.Fatal(err)
	}
	defer func() { _ = client.Close() }()

	// Loopback-адрес отклоняется ещё слоем предпроверки — сетевого соединения не происходит
	_, err = client.Get("http://127.0.0.1:9/")
	if err != nil {
		fmt.Println("Запрос перехвачен (без дозвона)")
	}
	// Вывод: Запрос перехвачен (без дозвона)
}
```

Слой соединений — последняя линия обороны: даже если `ValidateURL = false` отключил слой предпроверки, диалер всё равно разрешит домен и проверит реальные IP — когда все результаты разрешения приватные, вернётся ошибка вида `domain resolves only to blocked addresses`. Таймаут DNS-разрешения — `min(10s, Timeouts.Dial)`.

:::tip
У слоя предпроверки есть кэш уровня URL (1024 записи; при переполнении вытесняются самые старые 25%) — повторные запросы к тому же URL не выполняют разрешение и проверку заново. При переопределении на уровне запроса через `WithAllowPrivateIPs` кэш автоматически обходится (результат проверки одного и того же URL перестаёт быть стабильным и переиспользоваться не может).
:::

## Блокируемые диапазоны IP

HTTPC блокирует все IP-адреса, непригодные для публичного взаимодействия, покрывая IPv4, IPv6 и их обходные варианты.

### Блокируемые диапазоны IPv4

| Диапазон | CIDR | Описание |
|----------|------|----------|
| Loopback | `127.0.0.0/8` | localhost (включая весь диапазон 127.x.x.x) |
| Класс A приватные | `10.0.0.0/8` | Внутренняя сеть (RFC 1918) |
| Класс B приватные | `172.16.0.0/12` | Внутренняя сеть (RFC 1918) |
| Класс C приватные | `192.168.0.0/16` | Внутренняя сеть (RFC 1918) |
| Link-local | `169.254.0.0/16` | Автоконфигурация (включая метаданные AWS/Azure) |
| CGNAT | `100.64.0.0/10` | Carrier-grade NAT (включая метаданные Alibaba Cloud `100.100.100.200`) |
| Класс E зарезервированные | `240.0.0.0/4` | Зарезервированные адреса (`ip4[0] >= 240`) |
| «Эта сеть» | `0.0.0.0/8` | Идентификатор данной сети (`ip4[0] == 0`) |
| Выделение IETF для протоколов | `192.0.0.0/24` | Специальное назначение |
| TEST-NET-1 | `192.0.2.0/24` | Для документации (RFC 5737) |
| TEST-NET-2 | `198.51.100.0/24` | Для документации (RFC 5737) |
| TEST-NET-3 | `203.0.113.0/24` | Для документации (RFC 5737) |
| 6to4 relay | `192.88.99.0/24` | Устаревший anycast |

Кроме того, блокируются диапазоны IPv6 loopback (`::1`), уникальные локальные (`fc00::/7`), link-local (`fe80::/10`) и др. — IP-проверка HTTPC покрывает все зарезервированные категории: loopback, приватные, link-local unicast/multicast, multicast, unspecified.

### Блокируемые диапазоны IPv6

| Диапазон | CIDR | Описание |
|----------|------|----------|
| Loopback | `::1/128` | localhost |
| Уникальные локальные | `fc00::/7` | Внутренняя сеть (соответствует приватным IPv4) |
| Link-local | `fe80::/10` | Автоконфигурация |
| Префикс документации | `2001:db8::/32` | Для документации (RFC 3849) |
| NAT64 | `64:ff9b::/96` | Рекурсивная проверка встроенного IPv4 |

### Защита от обхода

HTTPC дополнительно блокирует следующие распространённые приёмы обхода SSRF:

| Приём | Пример | Защита |
|-------|--------|--------|
| IPv4-mapped IPv6 | `::ffff:127.0.0.1` | Нормализация к IPv4 с последующей проверкой |
| Десятичное целое | `2130706433` (= 127.0.0.1) | Распознавание как традиционного IP-литерала с блокировкой |
| Шестнадцатеричное | `0x7f000001`, `0x7f.0.0.1` | Распознавание префикса `0x` с блокировкой |
| Восьмеричное | `0177.0.0.1` | Распознавание ведущих нулей с блокировкой |
| Встроенный NAT64 | `64:ff9b::7f00:1` | Рекурсивная проверка встроенного IPv4 |

:::tip
Эта защита от обхода особенно важна в cgo-сборках: `getaddrinfo` может принимать традиционные IP-литералы и отображать их на приватные IP. HTTPC перехватывает эти формы ещё до разрешения DNS.
:::

## Защита endpoint метаданных облака

Службы метаданных инстансов (IMDS) облачных платформ — высокоценные цели SSRF-атак: одного доступа достаточно, чтобы похитить временные учётные данные. HTTPC по умолчанию блокирует эти адреса:

| Платформа | Адрес метаданных | Механизм блокировки |
|-----------|------------------|---------------------|
| AWS EC2 | `169.254.169.254` | Блокировка link-local `169.254.0.0/16` |
| Azure | `169.254.169.254` | Аналогично (блокировка link-local) |
| GCP | `metadata.google.internal` | Проверка IP после разрешения DNS |
| Alibaba Cloud | `100.100.100.200` | Блокировка CGNAT `100.64.0.0/10` |

:::warning
Хотя метаданные AWS IMDSv2 требуют токен, SSRF может сначала получить токен, а затем обратиться к данным. IP-блокировка HTTPC работает ниже уровнем, чем IMDSv2, — соединение перехватывается напрямую. Рекомендуется сочетать: блокировка HTTPC + включённый IMDSv2 как эшелонированная оборона.
:::

:::warning
Метаданные Alibaba Cloud (`100.100.100.200`) находятся в диапазоне CGNAT (`100.64.0.0/10`), который HTTPC **блокирует по умолчанию**. Если доступ к `100.64.0.0/10` действительно нужен для VPN (Tailscale/WireGuard и др.) или внутренней маршрутизации, его придётся явно исключить через `SSRFExemptCIDRs: []string{"100.64.0.0/10"}` — после исключения метаданные Alibaba Cloud в этом диапазоне также станут доступны, оцените риски.
:::

## Защита от перепривязки DNS

Перепривязка DNS (DNS Rebinding) — классический приём обхода SSRF-проверок. Злоумышленник управляет DNS-сервером домена: первое разрешение возвращает публичный IP (проверка проходит), а в момент фактического соединения — `127.0.0.1` (проверка обходится).

HTTPC применяет модель «разрешение - проверка - прямое подключение»:

1. **Разрешение**: домен разрешается в список IP
2. **Проверка**: каждый IP проверяется на приватность/зарезервированность
3. **Фильтрация**: заблокированные IP удаляются, остаются только разрешённые
4. **Прямое подключение**: дозвон идёт напрямую на проверенный IP, домен повторно не разрешается

```go
// Сценарий атаки:
// 1. Злоумышленник управляет DNS сервера evil.com
// 2. На этапе проверки разрешение возвращает публичный IP (проверка проходит)
// 3. Стандартный net/http повторно разрешает домен (теперь возвращается 127.0.0.1, проверка обходится)
//
// Защита HTTPC: при дозвоне используется уже проверенный IP, домен повторно не разрешается
```

:::tip
В среде «Split-Horizon DNS» (один домен разрешается и в публичные, и во внутренние IP) HTTPC автоматически отфильтрует приватные IP и установит соединение только по публичным, вместо того чтобы отказать всему домену.
:::

При включённом DoH (`Connection.EnableDoH = true`) работает та же линия обороны: результаты DoH-разрешения сначала проходят ту же IP-фильтрацию — если заблокированы все, возвращается ошибка `SSRF protection: domain resolves only to blocked addresses`, и лишь затем разрешённые IP пробуются по одному. Таймаут DNS-разрешения наследуется от контекста запроса с верхним пределом 10s (`min(10s, Timeouts.Dial)`); отмена запроса немедленно прекращает разрешение.

## Точные исключения SSRFExemptCIDRs

В микросервисной среде часто нужен доступ к сервисам внутри VPC, Kubernetes Service или VPN. `SSRFExemptCIDRs` позволяет точно исключить отдельные диапазоны CIDR, сохранив блокировку остальных приватных IP — это рекомендуемый способ доступа к внутренним сервисам.

```go
cfg := httpc.DefaultConfig()
cfg.Security.SSRFExemptCIDRs = []string{
    "10.0.0.0/8",       // внутренняя сеть VPC
    "100.64.0.0/10",    // Tailscale VPN
    "172.20.0.0/16",    // Kubernetes Service CIDR
}
client, _ := httpc.New(cfg)
```

### Типовые сценарии исключения

| Сценарий | CIDR | Описание |
|----------|------|----------|
| Внутренние сервисы VPC | `10.0.0.0/8` | VPC по умолчанию AWS/GCP/Azure |
| Tailscale VPN | `100.64.0.0/10` | Сеть Tailscale (RFC 6598) |
| Kubernetes | `172.20.0.0/16` и др. | Pod/Service CIDR |
| WireGuard | `10.13.0.0/16` и др. | Пользовательская сеть VPN |

Недействительный CIDR приведёт к ошибке `httpc.New()` (например, `SSRFExemptCIDRs: invalid CIDR "10.0.0/8"`) — конфигурация упадёт на этапе запуска, а не будет молча пропущена в рантайме.

:::warning
Исключаемые CIDR должны быть максимально точными. Избегайте слишком широких диапазонов (например, `0.0.0.0/0`) — это равносильно полному отключению защиты от SSRF. Даже для `10.0.0.0/8` оцените, нельзя ли сузить до фактически используемых подсетей.
:::

## Сравнение AllowPrivateIPs и SSRFExemptCIDRs

Оба варианта открывают доступ к внутренним сервисам, но семантика безопасности принципиально разная:

| Аспект | `AllowPrivateIPs = true` | `SSRFExemptCIDRs` |
|--------|--------------------------|-------------------|
| Состояние защиты | **Полный обход** SSRF-валидации | Исключаются только указанные CIDR, остальное блокируется |
| Охват | Все приватные/зарезервированные/loopback/link-local IP | Только перечисленные CIDR |
| localhost | Разрешён | Всегда блокируется — проверка имени хоста выполняется до сопоставления исключений, `SSRFExemptCIDRs` не может разрешить loopback-адреса (см. ниже «Известные границы») |
| Метаданные облака | **Доступны** (опасно) | По умолчанию блокируются |
| Уровень риска | Высокий — поверхность атаки как при отключённой SSRF | Низкий — точечное разрешение |
| Рекомендация | Только тесты / полностью внутренние клиенты | Рекомендуется для продакшена |

:::danger
`AllowPrivateIPs = true` полностью обходит SSRF-валидацию на уровне диалера (это не просто «разрешение приватных IP»), включая проверки localhost, link-local и всех зарезервированных адресов. Категорически недопустимо в продакшене при обработке любых недоверенных URL. Для доступа к внутренним сервисам используйте `SSRFExemptCIDRs`.
:::

## Исключение приватных IP на уровне запроса

Если клиент в целом использует безопасные умолчания (`AllowPrivateIPs = false`), а отдельным запросам нужен доступ к внутренней сети (например, к endpoint проверки здоровья на `localhost`), можно использовать опцию запроса `WithAllowPrivateIPs` — точечное разрешение без глобального ослабления политики безопасности:

```go
package main

import (
	"fmt"
	"log"

	"github.com/cybergodev/httpc"
)

func main() {
	// Клиент по умолчанию блокирует приватные IP; этот вызов разрешает их на уровне запроса
	result, err := httpc.Get("http://localhost:8080/health",
		httpc.WithAllowPrivateIPs(true),
	)
	if err != nil {
		log.Fatal(err)
	}
	fmt.Printf("Статус проверки здоровья: %d\n", result.StatusCode())
}
```

:::warning
Включайте `WithAllowPrivateIPs(true)` только для URL, которые **доверены и не происходят из пользовательского ввода**. Смысл SSRF-защиты — не дать злоумышленнику заставить ваш процесс обращаться к внутренним endpoint; отключение на уровне запроса вновь открывает этот риск для данного вызова. Если всему клиенту нужен доступ к внутренним сервисам, установите `Security.AllowPrivateIPs = true` в `Config`.
:::

Обратное применение тоже работает: если клиент настроен с `AllowPrivateIPs = true` (например, полностью внутренний клиент), а отдельному запросу нужно принудительно включить SSRF-проверку, используйте `WithAllowPrivateIPs(false)`.

## Проверка SSRF при перенаправлениях

Перенаправления — важный носитель SSRF-атак: публичный сервис может ответить 302 на `http://169.254.169.254/` (метаданные облака) или внутренний адрес. HTTPC выполняет SSRF IP-проверку и для целей перенаправлений.

| Конфигурация клиента | Поведение при перенаправлении на приватный IP |
|----------------------|-----------------------------------------------|
| `AllowPrivateIPs = false` (по умолчанию) | Блокировка — ошибка IP-проверки цели перенаправления |
| `AllowPrivateIPs = true` | Разрешение — обход SSRF (включая перенаправления) |
| `WithAllowPrivateIPs(true)` на уровне запроса | Разрешение перенаправления на приватный IP для данного запроса |
| Попадание в `SSRFExemptCIDRs` | Разрешение перенаправления в исключённый CIDR |

```go
// Сценарий: запрос к public-api.com, сервер отвечает 302 на http://169.254.169.254/
// HTTPC проверяет IP цели перенаправления и блокирует доступ к службе облачных метаданных
```

Каждый прыжок перенаправления проверяется в следующем порядке (отказ на любом шаге отклоняет прыжок; реализация — `checkRedirect` в `internal/engine/transport.go`):

1. **Белый список доменов** (если настроен `RedirectWhitelist`)
2. **Проверка протокола**: разрешены только http/https (отклоняются `file://`, `gopher://` и др.)
3. **SSRF-проверка хоста**: имя целевого хоста проверяется по правилам приватных/loopback/зарезервированных адресов
4. **Удаление конфиденциальных заголовков при кросс-доменном переходе**: если целевой хост отличается от исходного, удаляются `Authorization`, `Cookie`, `Proxy-Authorization` — даже если перенаправление разрешено, учётные данные не уедут на сторонний домен
5. **Обнаружение циклов перенаправления**: петли вида A→B→A возвращают ошибку (кроме подряд идущих одинаковых URL A→A)
6. **Лимит числа прыжков**: по умолчанию 10, жёсткий настраиваемый предел 50

Слой перенаправлений выполняет только быструю проверку имени хоста (без разрешения DNS — иначе повторное разрешение рядом со слоем дозвона открыло бы новое окно TOCTOU); реальные IP целевого домена повторно проверяются слоем дозвона при соединении — вместе два слоя не дают перенаправлениям обойти защиту от перепривязки DNS.

Точечное переопределение `WithAllowPrivateIPs` действует и на проверки перенаправлений: значение переопределения распространяется через context в валидатор перенаправлений и диалер (`internal/connection/ssrf_context.go`), поэтому цели перенаправлений такого запроса тоже оцениваются по переопределённой политике.

### Белый список доменов перенаправлений

`RedirectWhitelist` накладывает доменный контроль поверх IP-проверки, предотвращая уязвимости открытых перенаправлений:

```go
cfg := httpc.DefaultConfig()
cfg.Security.RedirectWhitelist = []string{
    "api.example.com",
    "auth.example.com",
    "*.cdn.example.com", // Подстановочный знак: строгие поддомены
}
// Перенаправления на домены вне белого списка блокируются
```

Подстановочный знак `*.example.com` совпадает со строгими поддоменами `api.example.com`, `static.cdn.example.com` и т.п., но **не** с голым доменом `example.com` (его нужно перечислять отдельно). При `nil` белом списке разрешено всё (поведение по умолчанию).

## Примеры конфигурации

### Безопасная конфигурация (обработка пользовательских URL)

При обработке пользовательских URL используйте `SecureConfig()` — самую строгую защиту от SSRF:

```go
cfg := httpc.SecureConfig()
// AllowPrivateIPs = false (строгий SSRF)
// FollowRedirects = false (блокирует SSRF через перенаправления)
// MaxResponseBodySize = 5MB
client, _ := httpc.New(cfg)
```

### Конфигурация внутренних сервисов (доступ к VPC)

Для доступа к внутренним сервисам VPC/Kubernetes используйте точные исключения `SSRFExemptCIDRs`:

```go
cfg := httpc.DefaultConfig()
cfg.Security.SSRFExemptCIDRs = []string{
    "10.0.0.0/8",     // VPC
    "172.20.0.0/16",  // Kubernetes Service
}
client, _ := httpc.New(cfg)
```

### Смешанная конфигурация (публичная сеть + внутренняя сеть)

Один клиент обращается и к публичным API, и к внутренним сервисам, причём диапазон внутренних сервисов известен:

```go
cfg := httpc.DefaultConfig()
cfg.Security.SSRFExemptCIDRs = []string{
    "10.50.0.0/16",   // Выделенная подсеть внутренних сервисов (точно)
}
cfg.Security.RedirectWhitelist = []string{
    "api.public.com",
    "*.internal.corp", // Разрешены перенаправления только на внутренние доверенные домены
}
client, _ := httpc.New(cfg)
```

## Полное отключение защиты от SSRF

Используйте только в тестовой среде. Два способа:

```go
// Способ 1: TestingConfig (одновременно отключает проверку TLS и другие функции безопасности)
client, _ := httpc.New(httpc.TestingConfig())

// Способ 2: ручная настройка
cfg := httpc.DefaultConfig()
cfg.Security.AllowPrivateIPs = true
client, _ := httpc.New(cfg)
```

`TestingConfig()` вне тестовой среды выводит предупреждение безопасности в `stderr` (см. [Обзор безопасности](./)).

:::danger
Никогда не устанавливайте `AllowPrivateIPs = true` в продакшене. Это полный отказ от SSRF-защиты: злоумышленник сможет добраться до облачных метаданных, внутренних сервисов и административных интерфейсов.
:::

## Известные границы и поверхности обхода

По исходному коду у SSRF-защиты есть следующие известные границы — учитывайте их при настройке:

### localhost нельзя исключить через CIDR

Проверка имени хоста `isLocalhost` в слое предпроверки выполняется **до** сопоставления исключений CIDR (`ValidateSSRFHost` в `internal/validation/netutil.go`: сначала проверяется localhost, затем исключения IP). Поэтому добавление `127.0.0.0/8` в `SSRFExemptCIDRs` не открывает `localhost` или `127.x.x.x` — запрос всё равно отклоняется слоем предпроверки. Если доступ к loopback-адресам действительно нужен, используйте `WithAllowPrivateIPs(true)` (уровень запроса) или `AllowPrivateIPs = true` (уровень клиента).

### Явно настроенные прокси не проходят SSRF-проверку

Адреса хостов прокси из `ProxyURL` и `ProxyPool` считаются **инфраструктурой, настроенной разработчиком**: при дозвоне SSRF-проверка и DoH-разрешение для них пропускаются (`internal/connection/pool.go`). Это сделано намеренно: разработчик, способный настроить прокси, и так может подключиться к любому адресу напрямую — перехват хостов прокси не добавляет реальной безопасности. Но у системного прокси есть ограничение: `EnableSystemProxy` определяет адрес прокси однократно при создании клиента (для исключения из SSRF); если переменные окружения разрешатся в localhost-прокси лишь позже (например, `127.0.0.1:7890`), такой прокси может быть заблокирован SSRF-защитой. Для динамически меняющихся локальных прокси задавайте `ProxyURL` явно.

### Произвольные поддомены localhost.* обрабатываются как обычные домены

Поддомены вида `localhost.*` (например, `localhost.example.com`) **не** считаются localhost — это могут быть легитимные публичные домены. Но если их DNS разрешается в loopback-IP, соединение всё равно перехватит слой дозвона — теряется лишь быстрая проверка слоя предпроверки без разрешения DNS.

### После отключения ValidateURL сдерживают слои перенаправлений и соединений

После отключения валидации URL (не рекомендуется — вне `TestingConfig` у этого почти нет оправданий) слой предпроверки не выполняется; слои перенаправлений и соединений продолжают работать. При этом литерал `localhost` в URL будет перехвачен только на уровне дозвона, после того как DNS разрешит его в loopback-IP, — с другим сообщением об ошибке (`domain resolves only to blocked addresses`), а быстрые проверки традиционных IP-литералов перестают действовать.

### Традиционные IP-литералы перехватываются до разрешения DNS

Записи вида `2130706433`, `0x7f000001`, `0177.0.0.1` отклоняются `net.ParseIP`, однако распознаватель `getaddrinfo` в cgo-сборке может их принять и отобразить на приватный IP. HTTPC распознаёт и перехватывает эти формы на слое предпроверки через `looksLikeLegacyIPLiteral` (правила распознавания: префикс `0x`, чисто числовая запись без точек, ведущие нули восьмерицы или шестнадцатеричные сегменты в многоточечной записи) — независимо от поведения платформенного распознавателя.

## Лучшие практики

1. Используйте `SecureConfig()` как базовую линию безопасности для обработки недоверенных URL
2. Исключайте через `SSRFExemptCIDRs` только действительно необходимые CIDR, избегайте `AllowPrivateIPs`
3. Настройте `RedirectWhitelist` для ограничения доменов целей перенаправлений
4. Отключайте перенаправления при обработке пользовательских URL (`FollowRedirects = false`)
5. Регулярно аудитируйте `SSRFExemptCIDRs` и удаляйте неиспользуемые диапазоны
6. Используйте `AuditMiddleware` для записи всех запросов — это помогает расследовать попытки SSRF-атак постфактум
