# Обзор безопасности

HTTPC следует принципу «Secure by Default» (безопасность по умолчанию): все ключевые функции безопасности работают из коробки и без дополнительной настройки противостоят типовым поверхностям атаки. При обработке пользовательских URL, вызовах внешних недоверенных сервисов или работе в сценариях с высокими требованиями безопасности (финансы, медицина, госсектор) многоуровневая защита HTTPC служит надёжной базовой линией.

## Матрица функций безопасности

Следующая таблица суммирует каждую функцию безопасности, соответствующее поле `Config`, значение по умолчанию и связанные функции/опции — для быстрого нахождения точки конфигурации.

| Функция | Поле Config | По умолчанию | Связанные функции / опции |
|---------|-------------|--------------|---------------------------|
| Минимальная версия TLS | `SecurityConfig.MinTLSVersion` | TLS 1.2 | — |
| Максимальная версия TLS | `SecurityConfig.MaxTLSVersion` | TLS 1.3 | — |
| Пользовательская конфигурация TLS | `SecurityConfig.TLSConfig` | `nil` (используется встроенная) | — |
| Пропуск проверки сертификата | `SecurityConfig.InsecureSkipVerify` | `false` | Только для тестов |
| Закрепление сертификатов | `SecurityConfig.CertificatePinner` | `nil` (отключено) | `NewSPKIHashPinner` и др. |
| Защита от SSRF | `SecurityConfig.AllowPrivateIPs` | `false` (включена) | `WithAllowPrivateIPs` |
| Точные исключения SSRF | `SecurityConfig.SSRFExemptCIDRs` | `nil` | — |
| Валидация URL | `SecurityConfig.ValidateURL` | `true` | — |
| Валидация заголовков | `SecurityConfig.ValidateHeaders` | `true` | — |
| Строгая проверка Content-Length | `SecurityConfig.StrictContentLength` | `true` | — |
| Проверка безопасности Cookie | `SecurityConfig.CookieSecurity` | `nil` (без проверки) | `StrictCookieSecurityConfig`, `WithSecureCookie` |
| Лимит размера тела ответа | `SecurityConfig.MaxResponseBodySize` | 10MB | — |
| Лимит размера тела запроса | `SecurityConfig.MaxRequestBodySize` | 0 (без лимита) | Требует явной установки |
| Защита от декомпрессионных бомб | `SecurityConfig.MaxDecompressedBodySize` | 100MB | — |
| Лимит размера заголовков ответа | `ConnectionConfig.MaxResponseHeaderBytes` | 0 (умолчание Go 10MB) | — |
| Белый список перенаправлений | `SecurityConfig.RedirectWhitelist` | `nil` (разрешены все) | — |
| Лимит числа перенаправлений | `RequestDefaults.MaxRedirects` | 10 | `WithMaxRedirects` |
| Следование перенаправлениям | `RequestDefaults.FollowRedirects` | `true` | `WithFollowRedirects` |

:::tip
При обработке пользовательских URL достаточно взять `httpc.SecureConfig()` — это самая строгая базовая линия безопасности: перенаправления отключены, лимит ответа 5MB, более короткие таймауты, включённая валидация URL/заголовков.
:::

## Карта многоуровневой обороны

Возможности безопасности HTTPC распределены по нескольким уровням жизненного цикла запроса: если один уровень обходят, следующий сдерживает атаку:

| Уровень | Момент | Что покрывает | Реализация |
|---------|--------|---------------|------------|
| Слой предпроверки | До отправки запроса | Проверка формата/протокола/длины URL, быстрая SSRF-проверка имени хоста (localhost, IP-литералы, традиционные записи), CRLF/управляющие символы в заголовках, размер тела запроса | `internal/security/validator.go` |
| Слой перенаправлений | Каждый прыжок 30x | Белый список доменов перенаправлений → SSRF-проверка цели → удаление конфиденциальных заголовков при кросс-доменном переходе → обнаружение циклов → лимит числа прыжков | `internal/engine/transport.go` |
| Слой соединений | При фактическом дозвоне | DNS разрешается однократно, каждый полученный IP проверяется, приватные адреса фильтруются, соединение устанавливается напрямую с проверенным IP (защита от TOCTOU перепривязки DNS) | `internal/connection/pool.go` |
| Слой TLS | При рукопожатии | Диапазон версий (по умолчанию 1.2-1.3), белый список шифров ECDHE+AEAD, предпочтения эллиптических кривых, запрет пересогласования, закрепление сертификатов | `internal/connection/pool.go` |
| Слой ответа | При чтении ответа | Двойной лимит (тело/распаковка), строгая проверка Content-Length, лимиты потокового чтения | `internal/engine/response.go` |
| Слой санитизации вывода | При записи логов/ошибок/аудита | Маскирование учётных данных в URL, чувствительные параметры запроса → `[REDACTED]`, маскирование конфиденциальных заголовков | `internal/validation/sanitize.go` |
| Слой загрузки | При записи файла | Пятислойная защита пути (UNC/управляющие символы/системные каталоги/path traversal/символические ссылки) и проверка целостности SHA-256 | `download.go` |

Трёхуровневое взаимодействие на примере SSRF: слой предпроверки первым перехватывает `localhost` и IP-литералы частных сетей по имени хоста (без разрешения DNS, нулевые сетевые накладные расходы); слой перенаправлений повторяет проверку для каждой цели; слой соединений разрешает DNS и проверяет реальные IP перед дозвоном — даже перепривязка DNS злоумышленнику едва ли поможет. Подробнее см. [Защита от SSRF](./ssrf).

## Поведение по умолчанию: из коробки vs требует включения

Значения по умолчанию приведены по исходному коду (`DefaultConfig()` в `types.go`).

### Включено по умолчанию (без настройки)

| Возможность | По умолчанию | Описание |
|-------------|--------------|----------|
| Защита от SSRF | `AllowPrivateIPs = false` | Блокирует приватные/зарезервированные/loopback/link-local IP, включая обход через IPv6 и смешанные записи |
| Валидация URL | `ValidateURL = true` | Разрешает только http/https, требует непустых scheme и host |
| Валидация заголовков | `ValidateHeaders = true` | Отклоняет CRLF-инъекции и управляющие символы, проверяет токены Connection/Transfer-Encoding |
| Диапазон версий TLS | TLS 1.2 – 1.3 | Отклоняет TLS 1.0/1.1; при нулевых значениях полей автоматически откатывается к 1.2/1.3 |
| Наборы шифров TLS | Белый список ECDHE+AEAD | 6 шифров с обязательной прямой секретностью; `RenegotiateNever` запрещает пересогласование |
| SSRF-проверка перенаправлений | Выполняется на каждом прыжке | Цели перенаправлений также проходят SSRF-валидацию |
| Удаление заголовков при кросс-доменном перенаправлении | Автоматически | При переходе на другой хост удаляются Authorization/Cookie/Proxy-Authorization |
| Обнаружение циклов перенаправления | Автоматически | Детекция петель вида A→B→A (кроме подряд идущих одинаковых URL) |
| Лимит перенаправлений | 10 | Настраиваемый предел 50, режима «без лимита» не существует |
| Лимит тела ответа | 10MB | Превышение возвращает ошибку |
| Защита от декомпрессионных бомб | 100MB | Ограничивает фактический размер после распаковки |
| Строгая проверка Content-Length | `StrictContentLength = true` | Ошибка при несовпадении числа байт ответа с Content-Length (кроме HEAD) |
| Маскирование логов/ошибок | Автоматически | Учётные данные в URL заменяются на `***:***`, параметры token/password и др. — на `[REDACTED]` |
| Защита пути загрузки | Автоматически | Пять уровней проверки + автоматическое удаление скачанного файла при провале проверки |
| HTTP/2 | `EnableHTTP2 = true` | Согласуется через ALPN при TLS |

### Выключено по умолчанию (требует явного включения)

| Возможность | По умолчанию | Как включить |
|-------------|--------------|--------------|
| Закрепление сертификатов | `CertificatePinner = nil` | Создать через `NewSPKIHashPinner` и др. и присвоить, см. [TLS и закрепление сертификатов](./tls-certpin) |
| Проверка безопасности Cookie | `CookieSecurity = nil` (без проверки) | `StrictCookieSecurityConfig()` |
| Белый список доменов перенаправлений | `RedirectWhitelist = nil` (разрешены все) | Настроить список доменов/шаблонов |
| Лимит тела запроса | `MaxRequestBodySize = 0` (без лимита, без отката) | Явно задать число байт |
| Таймаут заголовков ответа на уровне transport | `ResponseHeader = 0` (отключён) | Установить, когда нужна эшелонированная защита от slowloris |
| Cookie jar | `EnableCookies = false` | Установить true или использовать DomainClient |
| DoH | `EnableDoH = false` | Установить true |

:::tip
Пункты «выключено по умолчанию» — не дефект, а опции, чьи бизнес-требования нельзя предугадать: закреплению сертификатов нужны реальные отпечатки целевого сервиса, лимит тела запроса зависит от размера бизнес-сообщений. При обработке недоверенных URL `SecureConfig()` разом ужесточает многие из них (запрет перенаправлений, лимит ответа 5MB, более короткие таймауты).
:::

## Безопасность TLS

HTTPC по умолчанию требует TLS 1.2+ и отклоняет доказанно небезопасные TLS 1.0/1.1:

```go
cfg := httpc.DefaultConfig()
// По умолчанию уже TLS 1.2-1.3, вручную задавать не нужно
cfg.Security.MinTLSVersion = tls.VersionTLS12
cfg.Security.MaxTLSVersion = tls.VersionTLS13
```

Если нужно принудительно TLS 1.3 (более высокие требования безопасности, поддержка и клиента, и сервера), достаточно установить `MinTLSVersion = tls.VersionTLS13`. После установки `TLSConfig` поля `MinTLSVersion`/`MaxTLSVersion` игнорируются — приоритет у `TLSConfig`.

Конфигурация TLS по умолчанию (когда `TLSConfig` не задан) дополнительно включает следующие ужесточения:

- **Белый список шифров**: разрешены только 6 шифров ECDHE + AEAD с обязательной прямой секретностью (ECDSA/RSA × AES-128-GCM/AES-256-GCM/ChaCha20-Poly1305), CBC и статический обмен ключами RSA исключены
- **Предпочтения эллиптических кривых**: X25519, P-256, P-384
- **Запрет пересогласования**: `RenegotiateNever` — защита от атак класса renegotiation
- **Переиспользование сессий**: LRU-кэш клиентских билетов сессий (256 записей) ускоряет рукопожатие повторных соединений

Эти ужесточения HTTPC внедряет единообразно при создании transport (`createTLSConfig` в `internal/connection/pool.go`); если задан пользовательский `TLSConfig`, приоритет у вашей конфигурации — закрепление сертификатов всё равно добавляется поверх, остальные настройки шифров/кривых перестают действовать.

:::warning
`InsecureSkipVerify` — только для тестов. Никогда не устанавливайте `true` в продакшене: TLS-шифрование становится бессмысленным, и злоумышленник «посередине» может беспрепятственно перехватывать и подменять данные. При установке HTTPC выводит предупреждение безопасности в `stderr` вне тестовой среды (см. ниже «Механизм предупреждений безопасности»).
:::

Подробнее о TLS (шифры, закрепление сертификатов, mTLS, пользовательские CA) — в [TLS и закрепление сертификатов](./tls-certpin).

## Защита от SSRF

SSRF (Server-Side Request Forgery, подделка серверных запросов) — атака, при которой злоумышленник побуждает сервер отправлять запросы во внутреннюю сеть: можно похитить учётные данные облачных метаданных, просканировать порты внутренней сети, получить доступ к внутренним административным интерфейсам. HTTPC включает защиту от SSRF по умолчанию, блокируя соединения с приватными/зарезервированными диапазонами IP.

```go
cfg := httpc.DefaultConfig()
// AllowPrivateIPs = false (по умолчанию) → блокируются 127.0.0.1, 10.x, 192.168.x, 169.254.x и др.

// Точное исключение отдельных CIDR (например, VPN, внутренние сервисы VPC)
cfg.Security.SSRFExemptCIDRs = []string{
    "10.0.0.0/8",    // внутренняя сеть VPC
    "100.64.0.0/10", // Tailscale VPN
}

// Пресет с самой сильной защитой от SSRF
client, _ := httpc.New(httpc.SecureConfig())
```

### Блокируемые диапазоны IP

| Диапазон | CIDR | Описание |
|----------|------|----------|
| IPv4 loopback | `127.0.0.0/8` | localhost |
| Класс A приватные | `10.0.0.0/8` | Внутренняя сеть |
| Класс B приватные | `172.16.0.0/12` | Внутренняя сеть |
| Класс C приватные | `192.168.0.0/16` | Внутренняя сеть |
| Link-local | `169.254.0.0/16` | Автоконфигурация (включая метаданные AWS/Azure) |
| CGNAT | `100.64.0.0/10` | Carrier-grade NAT (включая метаданные Alibaba Cloud) |
| Класс E зарезервированные | `240.0.0.0/4` | Зарезервированные адреса |
| «Эта сеть» | `0.0.0.0/8` | Идентификатор данной сети |
| TEST-NET | `192.0.2.0/24` и др. | Для документации |
| IPv6 loopback | `::1/128` | localhost |
| IPv6 уникальные локальные | `fc00::/7` | Внутренняя сеть |
| IPv6 link-local | `fe80::/10` | Автоконфигурация |

> Выше перечислены основные диапазоны; полный список (включая IPv4-mapped IPv6, NAT64 `64:ff9b::/96`, префикс документации IPv6 `2001:db8::/32` и др.) см. в исходном коде `isPrivateOrReservedIP`. HTTPC также блокирует традиционные записи IP-литералов в десятичной/шестнадцатеричной/восьмеричной форме (например, `2130706433`, `0x7f000001`), предотвращая обход. Подробнее см. [Защита от SSRF](./ssrf).

## Валидация заголовков

`ValidateHeaders` (включена по умолчанию) автоматически предотвращает CRLF-инъекции и контрабанду запросов — отклоняет значения заголовков с возвратом каретки/переводом строки, нулевыми байтами и другими управляющими символами:

```go
// Следующие заголовки будут отклонены
httpc.WithHeader("X-Custom", "value\r\nInjected: header") // CRLF-инъекция
httpc.WithHeader("X-Bad", "value\x00null")                // Управляющие символы
```

Валидация использует поиск по таблице за O(1) — накладные расходы минимальны; `PerformanceConfig()` тоже сохраняет эту проверку.

Помимо CRLF и управляющих символов, многотокенные заголовки (синтаксис RFC 9110) дополнительно проходят **проверку токенов по белому списку**: в `Connection` разрешены только `keep-alive`/`close`/`upgrade`, в `Transfer-Encoding` — только `chunked`/`compress`/`deflate`/`gzip`/`identity`; это предотвращает контрабанду запросов (request smuggling).

## Санитизация ввода и маскирование в логах

HTTPC защищает и на **стороне вывода**: все URL, попадающие в логи, сообщения об ошибках и события аудита, проходят очистку `SanitizeURL` (`internal/validation/sanitize.go`), предотвращая вторичную утечку учётных данных и чувствительных параметров:

```go
// До очистки: https://user:pass@example.com/api?token=abc123&file=1
// После очистки: https://***:***@example.com/api?token=[REDACTED]&file=1
```

| Правило очистки | Описание |
|-----------------|----------|
| Маскирование учётных данных URL | `user:pass@host` → `***:***@host` |
| Обезличивание чувствительных параметров | Более 20 имён параметров, включая `token`, `access_token`, `api_key`, `password`, `signature` (без учёта регистра) → `[REDACTED]` |
| Удаление fragment | Защита от попадания в логи фрагментов неявного разрешения OAuth |

Эта очистка автоматически применяется к: URL при классификации ошибок (в `ClientError` не появляются исходные учётные данные), логам запросов `LoggingMiddleware`, событиям аудита `AuditMiddleware`, маскированию учётных данных прокси в `Config.String()`.

:::tip
Этот слой защищает от «вторичной утечки»: даже если атака сдержана другими уровнями, системы агрегации логов и ошибок (ELK, Sentry) всё ещё могут стать накопителем учётных данных. HTTPC по умолчанию обезличивает данные в источнике, без дополнительной настройки.
:::

## Безопасность Cookie

HTTPC предоставляет трёхуровневый контроль безопасности Cookie: уровень конфигурации (глобально), уровень сессии (`SessionManager`), уровень запроса (`WithSecureCookie`).

### CookieSecurityConfig

`CookieSecurityConfig` определяет обязательные атрибуты безопасности Cookie, защищая от CSRF, XSS, перехвата сессии:

| Поле | Описание | Default | Strict |
|------|----------|---------|--------|
| RequireSecure | Только передача по HTTPS | `false` | `true` |
| RequireHttpOnly | Запрет доступа из JS | `false` | `true` |
| RequireSameSite | Атрибут SameSite | `""` (без ограничений) | `"Strict"` |
| AllowSameSiteNone | Разрешить SameSite=None | `true` | `false` |
| RequireSecureForSameSiteNone | None требует Secure | `true` | `true` |

### Валидация уровня конфигурации (глобальная)

```go
cfg := httpc.DefaultConfig()
// Строгий режим: требуются Secure + HttpOnly + SameSite=Strict
cfg.Security.CookieSecurity = httpc.StrictCookieSecurityConfig()

// Или пользовательская настройка
cfg.Security.CookieSecurity = &httpc.CookieSecurityConfig{
    RequireSecure:   true,
    RequireHttpOnly: true,
    RequireSameSite: "Lax",
}
```

### Валидация уровня сессии

```go
sm, _ := httpc.NewSessionManagerDefault()
// Влияет на все последующие вызовы SetCookie, независимо от порядка добавления
sm.SetCookieSecurity(httpc.StrictCookieSecurityConfig())
```

### Валидация уровня запроса

```go
security := &httpc.CookieSecurityConfig{
    RequireSecure:   true,
    RequireHttpOnly: true,
}
// Внимание: WithSecureCookie должен идти после WithCookie — проверяются только Cookie, добавленные к этому моменту
result, err := client.Get("https://api.example.com",
    httpc.WithCookie(sessionCookie),
    httpc.WithSecureCookie(security),
)
```

:::warning
`WithSecureCookie` — это «последующая проверка» на уровне запроса: она валидирует только те Cookie, которые существуют на момент её применения. Обязательно помещайте её после всех опций `WithCookie`. Для глобальной валидации, не зависящей от порядка добавления, используйте `CookieSecurity` уровня конфигурации или `SetCookieSecurity` уровня сессии.
:::

## Защита от декомпрессионных бомб

Злоумышленник может использовать ответы gzip/deflate с высоким коэффициентом сжатия для исчерпания памяти (например, 10MB сжатых данных распаковываются в несколько GB). `MaxDecompressedBodySize` (по умолчанию 100MB) ограничивает фактический размер после распаковки, пресекая декомпрессионную бомбу в зародыше.

```go
cfg := httpc.DefaultConfig()
cfg.Security.MaxDecompressedBodySize = 50 * 1024 * 1024 // Лимит распаковки 50MB
```

### Приоритеты

| Конфигурация | Действующий лимит |
|--------------|-------------------|
| Задан только `MaxResponseBodySize` | Применяется он (строже) |
| Задан только `MaxDecompressedBodySize` | Лимит на размер после распаковки |
| Заданы оба | Действует меньший (более строгий) |

:::tip
`MaxResponseBodySize` ограничивает переданные байты до распаковки, `MaxDecompressedBodySize` — фактические байты после распаковки. Вместе они обеспечивают двухслойную защиту.
:::

## Лимит размера тела запроса

`MaxRequestBodySize` ограничивает размер загружаемого тела запроса, предотвращая сценарии, когда клиента побуждают отправить сверхбольшой запрос и исчерпать пропускную способность или память.

```go
cfg := httpc.DefaultConfig()
cfg.Security.MaxRequestBodySize = 5 * 1024 * 1024 // Лимит загрузки 5MB
```

:::warning
В отличие от `MaxResponseBodySize` (по умолчанию 10MB), `MaxRequestBodySize` по умолчанию равен **0 (без лимита)** и **не имеет автоматического резервного значения**. При обработке пользовательских загрузок или проксировании запросов обязательно устанавливайте лимит явно.
:::

## Безопасность перенаправлений

Перенаправления — частый носитель SSRF и открытых перенаправлений. HTTPC предоставляет многоуровневый контроль:

```go
// Сценарии, чувствительные к безопасности: полностью отключить перенаправления
cfg := httpc.SecureConfig() // FollowRedirects = false

// Или ограничить домены целей перенаправлений (поддерживаются шаблоны *.example.com)
cfg := httpc.DefaultConfig()
cfg.Security.RedirectWhitelist = []string{
    "api.example.com",
    "auth.example.com",
    "*.cdn.example.com",
}
```

`RedirectWhitelist` поддерживает точное сопоставление и подстановочные знаки: `*.example.com` совпадает со строгими поддоменами вроде `api.example.com`, но не с голым доменом `example.com` (оба нужно перечислять отдельно). Перенаправления на домены вне белого списка блокируются. Цели перенаправлений одновременно проходят SSRF IP-проверку.

Помимо белого списка, каждый прыжок перенаправления последовательно проходит следующие проверки (отказ на любом шаге отклоняет прыжок; реализация — `checkRedirect` в `internal/engine/transport.go`):

1. **Проверка протокола**: разрешены только http/https, остальные scheme (`file://` и др.) отклоняются
2. **SSRF-проверка цели**: имя хоста адреса перенаправления проверяется по правилам SSRF, цели вида `http://169.254.169.254/` отклоняются сразу
3. **Удаление конфиденциальных заголовков при кросс-доменном переходе**: если целевой хост отличается от исходного, автоматически удаляются `Authorization`, `Cookie`, `Proxy-Authorization` — даже если перенаправление разрешено, учётные данные не уедут на сторонний домен
4. **Обнаружение циклов**: петли вида A→B→A детектируются и возвращают ошибку (подряд идущие одинаковые URL A→A циклом не считаются, так как сервер может возвращать разные ответы)
5. **Лимит числа прыжков**: по умолчанию 10, жёсткий настраиваемый предел 50 (`MaxRedirects`), режима «без лимита» не существует

Управление следованием перенаправлениям, трассировка цепочки и ручная обработка — в [руководстве по перенаправлениям](../guides/redirects).

## Лимит размера заголовков ответа

`MaxResponseHeaderBytes` ограничивает размер заголовков ответа сервера, предотвращая сценарии, когда вредоносный сервер отправляет сверхбольшие заголовки для исчерпания памяти:

```go
cfg := httpc.DefaultConfig()
cfg.Connection.MaxResponseHeaderBytes = 1 * 1024 * 1024 // Лимит заголовков ответа 1MB
```

По умолчанию 0 означает использование значения стандартной библиотеки Go (10MB). В высокобезопасных сценариях рекомендуется сократить до 1MB.

## Механизм предупреждений безопасности

HTTPC выводит в `stderr` предупреждения о высокорисковых конфигурациях вне тестовой среды, напоминая разработчику своевременно исправить их. Предупреждение вызывают два типа конфигураций:

| Конфигурация | Условие срабатывания | Содержание предупреждения |
|--------------|----------------------|---------------------------|
| `InsecureSkipVerify = true` | Обнаруживается в `httpc.New()`, вне тестовой среды | Проверка TLS-сертификатов отключена |
| `TestingConfig()` | Проверяется при вызове, вне тестовой среды | Отключены проверка TLS, защита SSRF, валидация URL/заголовков |

`sync.Once` гарантирует, что каждое предупреждение сработает не более одного раза на процесс, чтобы не засорять логи. Тестовая среда определяется по суффиксу исполняемого файла `.test` / `.test.exe` либо по переменным окружения `GO_TEST` / `GOTEST=1`.

### Перенаправление или подавление предупреждений

```go
// Перенаправление в пользовательский writer (например, структурированный лог)
httpc.SetSecurityWarnOutput(os.Stdout)

// Полное подавление (не рекомендуется — предупреждения являются ограждением безопасности и не должны замалчиваться)
httpc.SetSecurityWarnOutput(io.Discard)
```

:::warning
`SetSecurityWarnOutput(io.Discard)` молча поглощает предупреждения безопасности. Используйте только после тщательного аудита конфигурации (например, подтвердив, что `TestingConfig` применяется только в тестовых бинарниках), и никогда не маскируйте предупреждения в продакшен-развёртывании.
:::

## Безопасность загрузки файлов

Путь файла в `Download` проходит пятислойную защиту `prepareFilePath`, предотвращая атаки path traversal и перезаписи файлов:

1. **Блокировка UNC-путей**: отклоняются сетевые пути вида `\\server\share`
2. **Фильтрация управляющих символов**: отклоняются пути с управляющими символами (`< 0x20`, `0x7F`, `0x00`)
3. **Защита системных путей**: запрещена запись в `/etc`, `/bin`, `C:\Windows` и другие системные каталоги (включая разрешение символических ссылок родительских каталогов)
4. **Детекция path traversal**: после `filepath.Clean` блокируется выход `../` за пределы рабочего каталога
5. **Защита от символических ссылок**: отклоняются пути, ведущие к символическим ссылкам; родительские каталоги проверяются рекурсивно против атак TOCTOU

После завершения загрузки можно проверить целостность файла через поле `Checksum` (SHA-256); при провале проверки скачанный файл автоматически удаляется.

## Промежуточное ПО аудита

`AuditMiddleware` генерирует структурированное событие аудита для каждого цикла запрос/ответ и подходит для сценариев со строгими требованиями соответствия (финансы, медицина, госсектор). URL автоматически обезличен (учётные данные удалены), конфиденциальные заголовки запроса (Authorization, Cookie и др.) по умолчанию маскируются.

```go
auditMiddleware := httpc.AuditMiddleware(&httpc.AuditConfig{
    OnAudit: func(event httpc.AuditEvent) {
        // event.URL уже обезличен; SourceIP/UserID извлекаются из context
        log.Printf("[AUDIT] %s %s -> %d (%v)",
            event.Method, event.URL, event.StatusCode, event.Duration)
    },
    Format:         "json",   // text или json
    IncludeHeaders: true,     // Записывать заголовки запроса/ответа (конфиденциальные маскируются)
    MaskHeaders:    []string{"Authorization", "Cookie", "Set-Cookie"},
    SanitizeError:  true,     // Очистка конфиденциальной информации в ошибках
})

cfg := httpc.DefaultConfig()
cfg.Middleware.Middlewares = []httpc.MiddlewareFunc{auditMiddleware}
```

`SourceIP` и `UserID` внедряются через ключи context: `httpc.SourceIPKey`, `httpc.UserIDKey`. Полные поля аудита, параметры конфигурации и практики продакшена — в [Контрольном списке для продакшена](./production-checklist).
