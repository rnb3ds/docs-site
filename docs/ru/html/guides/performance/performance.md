# Оптимизация производительности

Эта страница — обзор настройки производительности библиотеки html: сначала описываются **внутренние механизмы оптимизации** (чтобы помочь понять характеристики производительности), затем даются рекомендации по **настройке конфигурации**, **избеганию антипаттернов** и **методам бенчмаркинга**.

Если вам нужны полные детали по конкретной теме, см. специализированные страницы в этой же группе:

- [Повторное использование Processor и кэш](./processor-cache) — функции пакета vs экземпляры, механизм `sync.Pool`, стратегии кэширования и мониторинг попаданий
- [Пакетная обработка на практике](./batch-processing) — четыре пакетных API, структура `BatchResult`, управление параллелизмом и обработка частичных неудач

## Внутренние механизмы оптимизации

Библиотека html выполняет множество оптимизаций с нулевым выделением памяти и повторным использованием на горячих путях. Понимание этих механизмов помогает прогнозировать производительность различных сценариев использования и избегать конфликтов с оптимизациями библиотеки.

### Повторное использование Processor через sync.Pool

Функции пакета (например `html.Extract`) используют `sync.Pool` для повторного использования экземпляров `Processor`, избегая пересоздания тяжёлых объектов (детекторы кодировок, скореры и т.д.) при каждом вызове:

```text
html.Extract(data)
  → Получение Processor из sync.Pool (попадание в пул — повторное использование, иначе создание нового)
  → Выполнение извлечения
  → Возврат в sync.Pool (обнуление статистики + очистка журнала аудита + очистка кэша)
```

У пул-экземпляров Processor есть два ключевых решения в дизайне:

- **Отключение кэша**: у пул-экземпляров `MaxCacheEntries`, `CacheTTL`, `CacheCleanup` установлены в ноль. Поскольку пул-экземпляр вызывает `ClearCache()` при каждом возврате, включение кэша только добавляет накладные расходы на хэширование и фоновый goroutine очистки (`Get` всегда miss), но никогда не приводит к попаданию.
- **Передача пользовательского Config не использует пул**: когда вы вызываете `html.Extract(data, cfg)` с пользовательской конфигурацией, библиотека создаёт **временный Processor** (который сразу закрывается через `Close()`), а не повторно использует экземпляр из пула — потому что пул-экземпляры используют конфигурацию по умолчанию.

:::tip Подсказка
Пул-экземпляры отключают кэш. Если вы в цикле обрабатываете **потенциально повторяющееся** содержимое (дедупликация в краулере, сервисы за слоем кэша), создайте постоянный экземпляр `Processor` через `html.New()`, чтобы воспользоваться попаданиями в кэш. Подробнее в [Повторное использование Processor и кэш](./processor-cache).
:::

### Стратегия генерации ключа кэша

Ключ кэша — это значение `[16]byte` (128 бит), используемое напрямую как ключ `map`, **генерация ключа не вызывает выделения памяти в куче**. Входные данные для вычисления ключа включают:

- **UTF-8 содержимое** после преобразования кодировки (а не исходные байты) — одинаковое содержимое с разными объявлениями кодировки попадёт в одну запись кэша;
- Переключатели извлечения (`ExtractArticle`, `PreserveImages` и др., 5 логических флагов), упакованные в один `uint8`;
- Параметры форматирования (`InlineImageFormat`, `InlineLinkFormat`, `TableFormat`).

Для содержимого разного размера генерация ключа использует две стратегии:

| Размер содержимого | Стратегия | Описание |
|---------------------|-----------|----------|
| ≤ 64 КБ | Хэш полного содержимого | Вычисление xxHash-стиля по всем байтам, без риска коллизий |
| > 64 КБ | 5-точечная выборка | Голова + хвост + 3 равномерно распределённые точки, по 4096 байт на сегмент |

Выборка для больших документов ограничивает стоимость хэширования — полное хэширование документа 10 МБ свело бы на нет выигрыш от кэширования. 5-точечная выборка балансирует **устойчивость к хэш-флуду** (модификация в любой части документа с большой вероятностью меняет ключ) и **пропускную способность**.

### Предварительное выделение и пулинг объектов

Самые часто выделяемые объекты в процессе извлечения уже спулированы или предварительно выделены:

| Объект | Механизм | Назначение |
|--------|----------|------------|
| Построитель текста (`TrackedBuilder`) | `sync.Pool` | Повторное использование базовой ёмкости `[]byte` между вызовами, избегая роста с нуля до длины документа |
| Срез результатов ссылок | Предварительное выделение ёмкости 128 | Покрывает типичное количество ссылок на странице, избегая копирования массива при `append` |
| Стек проверки глубины (`depthStackEntry`) | `sync.Pool` | Повторное использование стека итеративной проверки глубины, избегая выделения стека при каждом извлечении |
| Временный буфер `[]byte` | `sync.Pool` | Повторное использование часто используемых небольших буферов для преобразования кодировки, конкатенации текста и т.д. |

:::warning Предупреждение
Сверхбольшие буферы отбрасываются пулом. Для предотвращения классической ловушки `sync.Pool` — «однократное извлечение сверхбольшого документа → пул навсегда содержит сверхбольшой буфер → все последующие мелкие запросы получают большой буфер» — буферы с ёмкостью более 64 КиБ **отбрасываются** при возврате, а не помещаются обратно в пул. Это означает, что обработка сверхбольших документов не получает преимуществ пулинга — это нормальное поведение.
:::

### Предвычисление строк форматирования

При `New()` значения `InlineImageFormat`/`InlineLinkFormat` предварительно вычисляются через `normalizeInlineFormat` (нижний регистр + trim + нормализация пустого значения к `"none"`) и сохраняются в полях `Processor`. Горячий путь извлечения напрямую сравнивает предвычисленные значения, **избегая вызова `strings.ToLower` при каждом извлечении**.

Эта оптимизация незначительна для однократного извлечения, но накапливается при пакетной обработке десятков тысяч документов.

### Ленивое выделение при извлечении медиа

Извлечение видео/аудио использует двухуровневую проверку, делая общий сценарий «контент без медиа» практически с нулевыми накладными расходами:

1. **Предварительная regex-проверка**: сначала быстрое сканирование через `HasMediaReference`, при подтверждении **отсутствия** медиа-ссылок все regex-сканирования и извлечение атрибутов iframe/embed/object пропускаются.
2. **Проверка размера**: при размере содержимого более 1 МБ (`maxHTMLForRegex`) regex-сканирование пропускается — выполнение regex на сверхбольших документах медленное и несёт риск ReDoS.
3. **Ленивая инициализация**: `ensureDedup` выделяет срез результатов и map дедупликации только при первом совпадении медиа. Документы без медиа — нулевое выделение на всём пути.

:::tip Подсказка
Если вас интересует только основной текст без изображений/видео/аудио, используйте [`TextOnlyConfig()`](../../api-reference/core/config#Предустановки-конфигурации) для однократного отключения сохранения всех медиа. В сочетании с описанным здесь ленивым механизмом накладные расходы на медиа стремятся к нулю.
:::

## Глубокая настройка кэша

Страница [Повторное использование Processor и кэш](./processor-cache) описывает базовое использование кэша и мониторинг попаданий. Здесь дополняются ключевые детали, влияющие на поведение кэша.

### Условия попадания

Попадание происходит только когда два ввода дают **одинаковый ключ кэша**, что означает:

- Одинаковое содержимое + одинаковая конфигурация → попадание;
- Одинаковая последовательность байтов, но с разными объявлениями кодировки (например, один и тот же текст с `charset=gbk` и `charset=utf-8`) → **попадание** (ключ вычисляется на основе UTF-8 текста после преобразования кодировки);
- Одинаковое содержимое, но разные переключатели `PreserveImages` и др. → **не попадание** (биты переключателей участвуют в вычислении ключа).

### Стоимость клонирования при попадании

Каждое попадание в кэш возвращает `cloneResult` (глубокая копия всего `Result`, включая срезы Images/Links/Videos/Audios). Это **необходимо** — записи в кэше читаются конкурентно, и если вернуть указатель напрямую, модификация результата вызывающим приведёт к загрязнению кэша через алиасинг.

Цена: когда `Result` содержит много ссылок/изображений, само клонирование вносит определённые накладные расходы. В сценариях с «очень высоким процентом попаданий + большим единичным результатом» (например, многократное извлечение одного и того же большого документа с плотными ссылками) эти затраты могут стать заметными.

### Когда отключать кэш

При `MaxCacheEntries = 0` метод `Extract` **полностью пропускает генерацию ключа** (не вычисляет хэш, не ищет в таблице, не записывает) — это настоящие нулевые накладные расходы, а не «включённый кэш, который всегда miss».

Отключение кэша подходит для сценариев **однократной обработки большого количества различного контента**:

```go
package main

import (
    "fmt"

    "github.com/cybergodev/html"
)

func main() {
    // Краулер обрабатывает огромное количество разных страниц: отключение кэша экономит хэширование и память
    cfg := html.DefaultConfig()
    cfg.MaxCacheEntries = 0 // Нулевые накладные расходы — пропуск всего слоя кэша
    cfg.CacheTTL = 0         // Также отключает фоновый goroutine очистки
    cfg.CacheCleanup = 0

    p, err := html.New(cfg)
    if err != nil {
        panic(err)
    }
    defer p.Close()

    // eachPage из реального потока скрапинга, практически не повторяется
    result, err := p.Extract([]byte("<html><body>Каждая страница разная</body></html>"))
    if err != nil {
        panic(err)
    }
    fmt.Println("Длина текста:", len(result.Text))
    // Вывод: Длина текста: ...
}
```

### Преобразование форматов не использует основной кэш

`ExtractToMarkdown` / `ExtractToMarkdownFromFile` внутри создают **временный Processor с отключённым кэшем** через `buildFormatProcessor` для выполнения преобразования формата. Это означает:

- Преобразование Markdown **не читает** и **не записывает** кэш основного Processor-а — даже если вы ранее извлекали тот же контент через `Extract`, `ExtractToMarkdown` не попадёт в кэш;
- Многократный вызов `ExtractToMarkdown` для одного и того же содержимого также не попадает в кэш друг для друга.

:::warning Предупреждение
Если вам нужно многократно получать Markdown для одного и того же содержимого, вместо нескольких вызовов `ExtractToMarkdown` лучше вызвать `Extract` один раз (с `InlineImageFormat`/`InlineLinkFormat` = `"markdown"`) — результат попадёт в основной кэш, и повторный ввод сможет попасть в кэш.
:::

## Тайм-ауты и управление Goroutine

`ProcessingTimeout` — это кооперативный тайм-аут, а не принудительное завершение. Понимание его контрольных точек и семантики ошибок помогает правильно обрабатывать тайм-ауты и отмену пользователем.

### Механизм кооперативной отмены

При `ProcessingTimeout > 0` библиотека создаёт производный дочерний context с deadline от переданного context, а функция обработки опрашивает `ctx.Done()` на **ключевых контрольных точках**:

- Перед определением кодировки
- Перед парсингом DOM
- Перед проверкой глубины
- Перед извлечением содержимого

Если крайний срок истёк, обработка прерывается на **следующей контрольной точке** и возвращается ошибка. Это означает, что тайм-аут не срабатывает мгновенно — работа между двумя контрольными точками (например, парсинг сверхбольшого документа) будет завершена.

### Глобальный лимит goroutine тайм-аута

Каждое извлечение с тайм-аутом занимает один goroutine до завершения или истечения. Для предотвращения утечки goroutine и исчерпания ресурсов библиотека устанавливает глобальный лимит `maxTimeoutGoroutines = 1000`. Когда количество конкурентных операций с тайм-аутом достигает лимита, новые извлечения **немедленно** возвращают `ErrProcessingTimeout` (вместо постановки в очередь).

:::warning Предупреждение
Параллелизм пакетного извлечения (`ExtractBatch`) ограничен `WorkerPoolSize` (по умолчанию 4, верхний предел 256), что обычно значительно ниже лимита в 1000 goroutine. Однако если вы на уровне приложения самостоятельно конкурентно вызываете большое количество `ExtractWithContext` с тайм-аутами, учитывайте этот глобальный лимит — он процессного уровня, общий для всех Processor.
:::

### Различение трёх источников отмены

При обработке тайм-аутов/отмен на уровне приложения следует различать источник по типу ошибки:

| Условие срабатывания | Возвращаемая ошибка | Значение |
|-----------------------|---------------------|----------|
| Истёк внутренний `ProcessingTimeout` библиотеки | `ErrProcessingTimeout` | Обработка одного документа превысила настроенный тайм-аут |
| Истёк deadline пользовательского context | `context.DeadlineExceeded` | Тайм-аут внешнего context (передаётся библиотекой как есть) |
| Ручная отмена context пользователем | `context.Canceled` | Активная отмена извне (передаётся библиотекой как есть) |

```go
package main

import (
    "context"
    "errors"
    "fmt"
    "time"

    "github.com/cybergodev/html"
)

func main() {
    cfg := html.DefaultConfig()
    cfg.ProcessingTimeout = 5 * time.Second // Внутренний тайм-аут библиотеки
    p, err := html.New(cfg)
    if err != nil {
        panic(err)
    }
    defer p.Close()

    // Внешний context для дополнительной страховки (может быть короче внутреннего тайм-аута)
    ctx, cancel := context.WithTimeout(context.Background(), 8*time.Second)
    defer cancel()

    result, err := p.ExtractWithContext(ctx, []byte("<html></html>"))
    switch {
    case errors.Is(err, html.ErrProcessingTimeout):
        fmt.Println("Внутренний тайм-аут: рассмотрите увеличение ProcessingTimeout или уменьшение ввода")
    case errors.Is(err, context.DeadlineExceeded):
        fmt.Println("Тайм-аут внешнего context")
    case errors.Is(err, context.Canceled):
        fmt.Println("Активная отмена вызывающим")
    case err != nil:
        fmt.Println("Другая ошибка:", err)
    default:
        fmt.Println("Успех, длина текста:", len(result.Text))
    }
    // Вывод: Успех, длина текста: ...
}
```

## Настройка производительности пакетной обработки

Страница [Пакетная обработка на практике](./batch-processing) подробно описывает использование пакетных API. Здесь фокусируется на нескольких точках настройки, влияющих на пропускную способность.

### Роль WorkerPoolSize

`WorkerPoolSize` ограничивает количество конкурентных goroutine через **семафор** (буферизованный channel), а не порождает неограниченно:

```text
ExtractBatch(items)
  → Создание extractor для каждого элемента
  → Цикл: сначала получить слот семафора (заблокировать при заполнении) → затем породить goroutine
  → Goroutine освобождает слот после завершения
```

Поэтому независимо от размера пакета **количество одновременно работающих извлечений** никогда не превышает `WorkerPoolSize`. Значение по умолчанию 4 подходит для смешанных I/O сценариев; для чисто CPU-интенсивных извлечений можно установить близко к `runtime.NumCPU()` (верхний предел 256).

```go
package main

import (
    "fmt"
    "runtime"

    "github.com/cybergodev/html"
)

func main() {
    cfg := html.DefaultConfig()
    // WorkerPoolSize: верхний предел 256, на многоядерных машинах нужно ограничить
    if n := runtime.NumCPU(); n > 256 {
        n = 256
    }
    cfg.WorkerPoolSize = n
    p, err := html.New(cfg)
    if err != nil {
        panic(err)
    }
    defer p.Close()

    pages := [][]byte{
        []byte("<html><body>Страница A</body></html>"),
        []byte("<html><body>Страница B</body></html>"),
    }
    br := p.ExtractBatch(pages)
    fmt.Printf("Успешно %d, неудачно %d\n", br.Success, br.Failed)
    // Вывод: Успешно 2, неудачно 0
}
```

### Лимиты пакета и отказоустойчивость

| Ограничение | Значение | Поведение |
|-------------|----------|-----------|
| Максимальное количество элементов в пакете | 10000 | При превышении — **весь пакет завершается неудачей** (каждый элемент возвращает ошибку), частичной обработки нет |
| Изоляция panic одного элемента | — | Panic при извлечении элемента перехватывается через `recover`, помечается только этот элемент как неудачный, не влияет на другие |

:::tip Подсказка
Пакетные методы экземпляра повторно используют кэш. Пакетные методы экземпляра `Processor` (`p.ExtractBatch`) внутри вызывают `p.Extract`, поэтому **разделяют и записывают в основной кэш** — при появлении повторяющегося содержимого в пакетной обработке последующие элементы попадают в кэш. Пакетная функция `html.ExtractBatch` использует пул-экземпляры с отключённым кэшем — этот эффект отсутствует. Для ускорения пакетной дедупликации предпочитайте методы экземпляра.
:::

## Управление вводом

Уменьшение объёма работы извлечения — наиболее прямой метод оптимизации:

- **Ограничьте `MaxInputSize`**: отклоняйте слишком большие документы, избегая ненужных накладных расходов на парсинг. По умолчанию 50 МБ, во многих сценариях можно уменьшить до 5–10 МБ.
- **Отключите ненужные переключатели извлечения**: при отключении `PreserveImages`/`PreserveVideos`/`PreserveAudios` и др., в сочетании с ленивым механизмом медиа соответствующие накладные расходы пропускаются.
- **Для чистого текста используйте `TextOnlyConfig()`**: уже отключает сохранение всех медиа, дополнительно отключите `ExtractArticle` для ускорения извлечения чистого текста.

```go
package main

import (
    "fmt"

    "github.com/cybergodev/html"
)

func main() {
    // TextOnlyConfig уже отключает сохранение всех медиа, дополнительная настройка не требуется
    cfg := html.TextOnlyConfig()
    cfg.MaxInputSize = 10 * 1024 * 1024 // 10 МБ, отклонять сверхбольшой ввод
    cfg.ExtractArticle = false           // Отключить распознавание статьи, чистый текст быстрее

    p, err := html.New(cfg)
    if err != nil {
        panic(err)
    }
    defer p.Close()

    result, err := p.Extract([]byte("<html><body><p>Только чистый текст</p></body></html>"))
    if err != nil {
        panic(err)
    }
    fmt.Println(result.Text)
    // Вывод: Только чистый текст
}
```

## Антипаттерны производительности

Ниже приведены распространённые, но снижающие производительность практики. Таблица поможет быстро их избежать:

| Антипаттерн | Проблема | Правильный подход |
|-------------|----------|-------------------|
| `html.New()` каждый раз в цикле | Создание+уничтожение Processor при каждой итерации, пересоздание детекторов кодировки, скореров и т.д. | Создать экземпляр вне цикла, повторно использовать внутри |
| Ожидание попаданий в кэш от функций пакета | Пул-экземпляры Processor отключают кэш, всегда miss | Использовать экземпляр `Processor` |
| Включение большого кэша для большого количества различного контента | Разбухание кэша, крайне низкий процент попаданий, лишние накладные расходы на память и хэширование | `MaxCacheEntries = 0` для отключения кэша |
| Ожидание попадания в основной кэш от `ExtractToMarkdown` | Преобразование формата использует временный Processor с отключённым кэшем | Настроить `InlineImageFormat="markdown"` и использовать `Extract` |
| Сверхбольшой HTML без тайм-аута | Злонамеренный/искажённый ввод может надолго занимать ресурсы | Установить `ProcessingTimeout` или использовать `ExtractWithContext` |
| Количество элементов пакета намного превышает `WorkerPoolSize`, ожидание линейного ускорения | Семафор ограничивает реальный параллелизм, большее количество не ускоряет | Настроить `WorkerPoolSize` по числу ядер CPU, разбить на пакеты |

## Рекомендации по бенчмаркингу

Использование Go benchmark для количественной оценки влияния изменений конфигурации и попаданий в кэш — самый надёжный метод оптимизации производительности.

### Базовый бенчмарк извлечения

<!-- check-code: skip -->
```go
package html_test

import (
    "os"
    "testing"

    "github.com/cybergodev/html"
)

// Подготовьте репрезентативный реальный HTML (не используйте крошечные синтетические фрагменты)
var benchDoc, _ = os.ReadFile("testdata/sample.html")

// BenchmarkExtract измеряет базовую производительность однократного извлечения (включая определение кодировки, парсинг, скоринг, извлечение)
func BenchmarkExtract(b *testing.B) {
    p, _ := html.New(html.DefaultConfig())
    defer p.Close()

    b.ReportAllocs() // Ключевое: наблюдайте количество выделений памяти в куче на каждое извлечение
    b.ResetTimer()
    for i := 0; i < b.N; i++ {
        _, err := p.Extract(benchDoc)
        if err != nil {
            b.Fatal(err)
        }
    }
}
```

### Измерение выгоды от попаданий в кэш

Сравнение «повторное извлечение одинакового содержимого» и «каждый раз разное содержимое» покажет, действительно ли кэш помогает:

<!-- check-code: skip -->
```go
// BenchmarkExtractCacheHit многократно извлекает один и тот же контент, со второго раза должно попадать в кэш
func BenchmarkExtractCacheHit(b *testing.B) {
    p, _ := html.New(html.DefaultConfig())
    defer p.Close()
    p.Extract(benchDoc) // Прогрев кэша

    b.ReportAllocs()
    b.ResetTimer()
    for i := 0; i < b.N; i++ {
        _, _ = p.Extract(benchDoc)
    }
}

// BenchmarkExtractNoCache — отключённый кэш как контрольная группа
func BenchmarkExtractNoCache(b *testing.B) {
    cfg := html.DefaultConfig()
    cfg.MaxCacheEntries = 0
    p, _ := html.New(cfg)
    defer p.Close()

    b.ReportAllocs()
    b.ResetTimer()
    for i := 0; i < b.N; i++ {
        _, _ = p.Extract(benchDoc)
    }
}
```

### Сравнение различных конфигураций

Используйте подтесты `b.Run` в одном бенчмарке для сравнения нескольких конфигураций:

<!-- check-code: skip -->
```go
func BenchmarkConfigs(b *testing.B) {
    cases := []struct {
        name string
        cfg  func() html.Config
    }{
        {"Default", html.DefaultConfig},
        {"TextOnly", html.TextOnlyConfig},
        {"NoCache", func() html.Config {
            c := html.DefaultConfig()
            c.MaxCacheEntries = 0
            return c
        }},
    }
    for _, tc := range cases {
        b.Run(tc.name, func(b *testing.B) {
            p, _ := html.New(tc.cfg())
            defer p.Close()
            b.ReportAllocs()
            b.ResetTimer()
            for i := 0; i < b.N; i++ {
                _, _ = p.Extract(benchDoc)
            }
        })
    }
}
```

:::tip Подсказка
Интерпретация результатов бенчмарка:
- `ns/op`: время одного извлечения — чем меньше, тем быстрее;
- `B/op` и `allocs/op`: байты и количество выделений в куче на одно извлечение — ключевой показатель для определения «работает ли пулинг» и «попадает ли кэш»: при попадании в кэш `allocs/op` значительно снижается;
- Сравните `CacheHit` и `NoCache`: если значения близки, ваш контент **не повторяется**, кэш — чистая нагрузка, его следует отключить.
:::

Запуск бенчмарков:

```bash
go test -bench=. -benchmem ./...          # Запустить все бенчмарки, отчитаться о выделении памяти
go test -bench=BenchmarkExtract -count=5  # Многократный запуск для наблюдения колебаний
```
